# WBS 공정표 규칙 (wbs)

공정표는 프로젝트마다 파일 하나(`data/wbs/<프로젝트 id>.json`)다. 화면(프로젝트 → 카드 → WBS)이 이 파일을 그대로 읽고, 파일을 고치면 열려 있는 화면이 바로 따라 바뀐다.
그래서 형식이 틀리면 화면에 경고가 뜬다. 아래 형식을 정확히 지킨다.
**날짜 계산법·`id` 만드는 법·지우기 규칙·프로젝트 목록(`data/db/projects.json`) 형식은 platform 스킬(`.claude/skills/platform/SKILL.md`)을 따른다.** 이 문서와 함께 읽는다.

## 파일 형식

`{ "bac": 계약금액(원) 또는 null, "ac": 실제 비용 누적(원) 또는 null, "items": [ … ], "actualLog": { … } }`.
맨 위 필드: `bac`(계약금액), `ac`(실제 비용 누적), `items`(항목 목록), `actualLog`(날짜별 전체 실제 진도 — 화면이 저장할 때마다 자동으로 적는다. 새로 만들 때는 `{}`).
`bac`·`ac` 는 주인이 금액을 말했을 때만 숫자(원)로 넣고, 아니면 `null`.
`items` 항목 하나(작업 하나 또는 대단락 하나):

| 필드 | 뜻 |
|---|---|
| `code` | `1`, `1.1`, `1.1.1` 모양의 번호 (아래 "코드") |
| `type` | 자식이 있으면 `대단락`, 없으면 `작업` |
| `name` | 작업명 |
| `owner` | 담당. 말하지 않았으면 `""` |
| `start` | 시작 날짜 `YYYY-MM-DD` — **작업만** |
| `end` | 완료 날짜 — **작업만**. `start` 보다 빠르면 안 된다 |
| `weight` | 가중치 (아래 "가중치") |
| `progress` | 진도율 0~100 숫자 — **작업만**. 새로 만들 때는 **0** |
| `memo` | 메모. 없으면 `""` |

- **대단락의 `start`·`end`·`progress` 는 쓰지 않는다.** 화면이 하위 작업에서 자동으로 계산한다(진도율은 하위의 가중 평균). 상태(완료·진행·지연·대기)와 EVMS 숫자도 화면이 계산하니 적지 않는다. `actualLog` 도 고치지 않는다.
- `data/wbs/_history/<프로젝트 id>/` 는 화면의 "Rev 저장"이 만든 저장 이력 보관 폴더다. 읽을 수는 있지만 고치거나 지우지 않는다.

## 코드 붙이는 법

- 대단락은 말한 순서대로 `1`, `2`, `3` …. 그 아래 작업은 `1.1`, `1.2` …. 작업을 더 쪼개야 할 때만 `1.1.1` (보통 두 단계까지).
- **1 부터 빈틈없이** 붙이고, 같은 코드를 두 번 쓰지 않는다. 위 번호가 있어야 한다(`1.1.1` 은 `1.1` 이 있어야 함).
- 파일 안의 항목 순서는 코드 순서(`1`, `1.1`, `1.2`, `2`, `2.1` …). 번호 비교는 숫자로 한다(`1.10` 은 `1.9` 뒤).
- 작업을 새로 더할 때는 그 대단락의 마지막 번호 다음 번호로 맨 끝에 덧붙인다(`3.4` 다음은 `3.5`). 중간에 끼워야 하면 뒤 항목들(하위 포함)의 번호를 한 칸씩 밀고, 번호가 바뀐 것을 알린다.

## 가중치: 같은 부모 아래 형제끼리 합이 100

- 대단락끼리 합 100, 각 대단락 안의 작업끼리도 합 100. 정수로 쓰고, 합이 정확히 100 이 되게 가장 큰 것(또는 마지막 것)으로 맞춘다.
- 주인이 가중치를 말했으면 그대로 쓴다(합이 100 이 아니면 비율로 환산하고 알린다).
- 말하지 않은 **대단락**은 일의 양을 가늠해 정한다. 이름이 비슷하면 이 값을 기준으로, 합이 100 이 되게 비율로 맞춘다.

| 대단락 이름 | 설계 | 구매·자재 | 제작·가공 | 용접 | 검사 | 출하 | 그 밖 |
|---|---|---|---|---|---|---|---|
| 기본 가중치 | 15 | 15 | 20 | 25 | 15 | 10 | 10 |

  예: 설계·자재·가공·용접·검사·출하 → 15+15+20+25+15+10 = 100 (그대로). 설계·제작·검사 → 15·20·15 를 합 100 으로 환산 → 30·40·30.
- 말하지 않은 **작업**끼리는 작업량이 비슷하다고 보고 똑같이 나눈다(3개면 34·33·33 — 나머지는 앞 작업에).

## 기간: 작업의 시작·완료는 프로젝트 기간 안

- 모든 작업의 `start`·`end` 는 프로젝트 기간(시작일 ~ 종료일) 안이다. `start` 가 `end` 보다 늦으면 안 된다. 기간은 달력일(주말 포함).
- **날짜는 platform 스킬의 규칙으로 정확히 계산한다.** 월말(28·29·30·31일)과 해가 바뀌는 곳을 어림짐작하지 않는다.
- 배치 방법(순서대로 이어 붙인다):
  1. 프로젝트 전체 일수 `N` = 종료일 − 시작일 + 1.
  2. 대단락별 일수 = `N` × (그 대단락 가중치 ÷ 100). 소수는 반올림하고, **마지막 대단락**의 일수로 합이 `N` 이 되게 맞춘다.
  3. 대단락 구간은 첫 대단락이 프로젝트 시작일에서 시작하고, 앞 구간이 끝난 **다음 날** 뒤 구간이 시작하며, 마지막 대단락이 종료일에 끝난다. (구간 = 시작일 + 앞 일수 합, 끝 = 시작 + 일수 − 1)
  4. 각 대단락의 구간을 그 안의 작업들에게 같은 방식으로(작업 가중치 비율, 마지막 작업으로 맞춤) 나눈다. 대단락 일수가 작업 수보다 적으면 작업 수를 줄인다(작업 하나는 1일 이상).
- 쓰고 나서 모든 작업의 날짜가 프로젝트 기간 안인지, 구간이 끊기거나 겹치지 않는지 다시 확인한다.

## "WBS 짜 줘: 프로젝트, 기간, 대단락" — 만들기

요청에서 읽어 낼 것: 고객사 · 프로젝트 이름 · 시작일 · 종료일 · 대단락 목록(말한 순서). 예: `WBS 짜 줘: 가나다전자 압력용기 개조, 2026-11-01부터 2027-02-28까지, 대단락은 설계·자재·가공·용접·검사·출하`
→ 고객사 `가나다전자`, 이름 `압력용기 개조`. 회사 이름처럼 보이는 앞말이 고객사, 나머지가 프로젝트 이름이다. 애매하면 전체를 이름으로 하고 고객사는 `""`. 기간이나 대단락이 빠졌으면 **한 번만** 짧게 물어본다.

순서:
1. `data/db/projects.json` 을 읽는다(없으면 `[]`). **이름과 고객사가 모두 같은** 프로젝트가 있으면 그 `id` 를 쓰고 그 프로젝트의 기간을 바꾸지 않는다(요청 기간이 다르면 알린다). 이름만 같고 고객사가 다르면 **다른 프로젝트**로 새로 만든다 — 같은 이름의 프로젝트가 이미 있다고 답에 한 줄로 알린다.
2. 없으면 프로젝트 목록 **맨 끝에** 새 항목을 덧붙인다(다른 항목은 한 글자도 바꾸지 않는다). `id` 는 platform 스킬 규칙(영문 소문자·숫자 8자)으로 만든다.
   `{ "id": "p7m2x9ab", "name": "예시 탱크 제작", "client": "예시산업", "status": "계획", "progress": 0, "start": "2026-04-01", "due": "2026-06-29", "owner": "" }`
   (`status` 는 새 프로젝트면 `계획`, `progress` 는 `0`, `owner` 는 말하지 않았으면 `""`.)
3. `data/wbs/<그 프로젝트 id>.json` 이 **이미 있으면 덮어쓰지 않는다.** 사람이 고친 공정표일 수 있으니 "이미 공정표가 있어요. 새로 짤까요?" 하고 먼저 묻는다. 없으면 만든다.
4. 대단락 가중치를 정하고(위 표), 기간을 배치하고, 대단락마다 작업을 2~4개로 쪼갠다. 작업 이름은 아래 "작업 쪼개기"를 참고하되 업종에 맞게 정한다. 모든 작업의 `progress` 는 `0`.
5. 파일 전체를 한 번에 쓴다(JSON, 들여쓰기 2칸 또는 위 예처럼 항목 한 줄씩). 쉼표·따옴표·대괄호를 틀리지 않게.
6. **파일을 다시 읽어 확인한다**: (가) JSON 이 올바르다 (나) 코드가 1 부터 빈틈없고 겹치지 않으며 위 번호가 있다 (다) 같은 부모 아래 `weight` 합이 100 이다 (라) 모든 작업의 날짜가 프로젝트 기간 안이고 `start` ≤ `end` 이며 구간이 이어진다 (마) 작업의 `progress` 가 모두 0 이고 대단락에는 `start`·`end`·`progress` 가 없다. 틀렸으면 바로 바로잡는다.
7. 답: 한 줄 요약 + 대단락별 표(대단락 · 기간 · 가중치 · 작업 수)를 짧게. 마지막에 "프로젝트 메뉴에서 카드를 누르면 공정표가 열려요" 라고 알린다.

### 작업 쪼개기 (참고: 플랜트 기기 제작)

| 대단락 | 작업 예 |
|---|---|
| 설계 | 기본설계 · 상세설계·제작도면 · 고객 도면 승인 |
| 구매·자재 | 자재 발주 · 자재 입고·검사 · 부속품 구매 |
| 제작·가공 | 판재 절단·성형 · 기계 가공 · 조립 |
| 용접 | 용접 절차서 승인 · 본체 용접 · 노즐 용접 · 용접 후 열처리 |
| 검사 | 비파괴검사 · 수압시험 · 최종 치수·외관 검사 |
| 출하 | 도장·포장 · 출하·운송 |

## "○○ 진도율 60%로" — 고치기

예: `압력용기 개조 공정표에서 용접의 첫 작업 진도율 40%로`

1. **프로젝트 찾기**: 말한 이름과 맞는 프로젝트(`data/db/projects.json`)를 모두 찾고, 그중 `data/wbs/<id>.json` 이 있는 것을 쓴다. 후보가 둘 이상이거나 하나도 없으면 후보를 보여 주고 어느 것인지 묻는다. 말이 없었으면 가장 최근에 다룬 프로젝트.
2. **항목 찾기**: 이름이 맞는 **작업**(부분 일치 가능) 또는 코드(`3.2`). `○○의 첫 작업` = 대단락 `○○` 의 첫 하위(`N.1`), `마지막 작업` = 마지막 하위. 같은 이름이 여럿이면 후보(코드와 이름)를 보여 주고 묻는다.
3. **대단락은 진도율을 직접 못 바꾼다**(하위 작업의 가중 평균으로 자동 계산). 대단락을 가리키면 그렇게 알리고, 하위 작업 중 어느 것인지 묻는다.
4. **값**: `60%로` → 60. `10% 올려` → 지금 값 + 10(100 을 넘지 않게). `끝났어`·`완료` → 100. 0~100 숫자 하나만 쓴다.
5. 그 작업의 `progress` **숫자 하나만** 고친다. 다른 항목·다른 필드는 한 글자도 바꾸지 않는다. 고친 뒤 파일을 다시 읽어 JSON 이 올바른지 확인한다.
6. 답 한 줄: `용접 절차서 승인(4.1) 진도율 0% → 40%`. 가능하면 대단락의 새 진도율도 알린다 — 대단락 진도율 = Σ(하위 작업 가중치 × 진도율) ÷ Σ(하위 작업 가중치).

## 그 밖의 수정

- 작업 추가·이름·담당·기간 변경도 해당 항목만 고친다. 작업을 추가하면 같은 대단락 안의 가중치 합이 100 이 되게 다른 작업들을 조정하고, 조정했다고 알린다. 기간을 바꿀 때도 프로젝트 기간 안에 둔다.
- 주인이 계약금액(BAC)·실제 비용(AC)을 말하면 `bac`·`ac` 에 원 단위 숫자로 넣는다(`12억` → `1200000000`).
- 항목을 **지우는 일은 먼저 물어보고** 허락받은 뒤에만 한다(대단락을 지우면 하위도 함께 지워지니 개수를 알려 준다). 지운 뒤 번호는 1 부터 다시 빈틈없이 맞춘다.
- 말하지 않은 값은 지어내지 않는다. 확실하지 않으면 파일을 읽어 후보를 말하고 묻는다.
